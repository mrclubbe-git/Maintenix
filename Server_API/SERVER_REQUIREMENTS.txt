MAINTENIX SERVER REQUIREMENTS
=============================

Purpose
-------
This document describes what is required from the Linux server when the Maintenix
Web UI is hosted on GitHub Pages and the Maintenix Server_API runs on a separate
server for testing.

The browser will load the Web UI from:
    https://mrclubbe-git.github.io/Maintenix/

The Web UI must then be able to reach the Server_API through a browser-accessible
HTTPS address, for example:
    https://api.example.com


1. OPERATING SYSTEM
-------------------
Required:
- Linux server.
- 64-bit installation recommended.
- Normal command-line access.
- Git installed.
- curl installed for health checks.

Why Linux:
- The current server-status endpoint reads /proc/stat for CPU information.
- It also uses the Linux "df -P" command for disk statistics.
- Running on Linux therefore supports the complete current Server_API feature set.


2. NODE.JS AND NPM
------------------
Required:
- Node.js 18 or newer.
- npm.

Recommendation:
- Use a currently maintained Node.js LTS release rather than the minimum version.

The Server_API dependency tree contains packages that require Node.js >= 18.


3. APPLICATION FILES
--------------------
The server needs a checked-out copy of the Maintenix repository, specifically:
    Maintenix/Server_API

Typical installation:
    git clone https://github.com/mrclubbe-git/Maintenix.git
    cd Maintenix/Server_API
    npm ci

For an existing installation:
    cd Maintenix
    git pull
    cd Server_API
    npm ci


4. REQUIRED SERVER PROCESSES
----------------------------
Maintenix currently has three server-side processes that must run:

1. API server
   - index.js

2. Servicing worker
   - servicingWorker.js

3. Call-out worker
   - calloutWorker.js

The repository includes a launcher that starts all three:

    npm run start:all

Do not run multiple copies of the workers unless this is deliberately designed for,
because duplicate workers could process the same application workload unexpectedly.


5. API PORT
-----------
Default internal API port:
    5055

The API listens on:
    0.0.0.0:5055

The port can be overridden with the PORT environment variable, for example:
    PORT=5056 npm run start:all

For a normal HTTPS deployment, port 5055 should preferably remain private and be
accessed through a reverse proxy.


6. HTTPS IS REQUIRED FOR THE GITHUB PAGES TEST SETUP
----------------------------------------------------
The GitHub Pages Web UI is served over HTTPS.

The API should therefore also be exposed using HTTPS, for example:
    https://api.example.com

Do not rely on a normal HTTP URL such as:
    http://server-ip:5055

for browser testing from GitHub Pages. Browsers can block an HTTP API requested by
an HTTPS page as mixed content.

Recommended layout:

    Internet / Browser
            |
          HTTPS 443
            |
       Nginx or Caddy
            |
      127.0.0.1:5055
            |
       Maintenix API

A valid, browser-trusted TLS certificate is required.

Let's Encrypt is suitable for a normal public DNS hostname.


7. DNS
------
Recommended:
- A DNS hostname dedicated to the API, for example:
      api.example.com

The DNS A/AAAA record should resolve to the Linux server.

Using a hostname is strongly preferred over exposing a raw IP because HTTPS
certificate management is much simpler and more reliable.


8. FIREWALL / NETWORK ACCESS
----------------------------
Recommended externally accessible ports:

- TCP 443
  Required for the public HTTPS API.

- TCP 80
  Optional, but commonly used for HTTP-to-HTTPS redirect and Let's Encrypt
  certificate issuance/renewal.

- TCP 22
  SSH administration only.
  Restrict this to trusted source addresses where possible.

Recommended:
- Do NOT expose TCP 5055 directly to the public Internet when a reverse proxy is
  being used.
- Bind/restrict firewall access so the reverse proxy is the normal public entry point.


9. CORS
-------
The Server_API must allow the GitHub Pages origin:

    https://mrclubbe-git.github.io

The current Maintenix Server_API already includes this origin in its default CORS
allow-list.

If the UI is later moved to a custom domain, configure CORS_ORIGINS accordingly.

Example:
    CORS_ORIGINS=https://mrclubbe-git.github.io,https://app.example.com

Only origins that actually require browser access should be included.


10. PERSISTENT AND WRITABLE DATA
--------------------------------
The application uses files below:

    Server_API/data/

The account running Maintenix must have read/write access to application data that
the API and workers update.

This includes generated/uploaded content and application JSON data.

Important:
- Preserve the Server_API/data directory during application updates.
- Preserve the template files used by report/document generation.
- Ensure Server_API/data/uploads and any generated subdirectories are writable.
- Do not run the application from a read-only filesystem.


11. BACKUPS
-----------
Back up at minimum:

    Server_API/data/

This directory contains application state, uploaded/generated files and supporting
data used by the current file-based backend.

Recommended:
- Automated daily backups.
- Multiple backup generations.
- At least one backup copy outside the application server.
- Test restoration periodically.


12. SERVICE ACCOUNT
-------------------
Recommended:
- Run Maintenix under a dedicated non-root Linux user.
- The service user should own or have appropriate access to the Server_API data
  directories.
- Do not run the Node.js application as root unless there is a specific operational
  reason.


13. PROCESS SUPERVISION
-----------------------
For anything beyond a temporary terminal test, use a process supervisor such as:

- systemd (preferred on most Linux servers), or
- another suitable Node/process supervisor.

The supervisor should:
- Start Maintenix automatically after reboot.
- Run:
      npm run start:all
- Restart the stack if it exits unexpectedly.
- Capture stdout/stderr logs.
- Run as the dedicated Maintenix service account.
- Use the Server_API directory as its working directory.


14. REVERSE PROXY
-----------------
Recommended:
- Nginx or Caddy in front of the Node.js API.
- Public HTTPS on port 443.
- Proxy requests to:
      http://127.0.0.1:5055

The proxy should preserve normal HTTP headers and support request bodies large
enough for Maintenix uploads.

The API currently accepts JSON/form request bodies up to 25 MB, so the reverse
proxy upload/body-size limit must not be lower than the application requirement
when those upload features are being tested.


15. GITHUB PAGES API CONFIGURATION
----------------------------------
Once the server has a working HTTPS API hostname, set the GitHub repository
variable:

    MAINTENIX_API_BASE_URL

Example value:
    https://api.example.com

Then rebuild/redeploy the "deploy" branch.

The Web UI will use that base URL for API and uploaded-file requests.

Recommended:
- Use the origin only, without a trailing path.
- Example:
      https://api.example.com
- Do not include "/api" in MAINTENIX_API_BASE_URL because the Web UI already uses
  routes such as /api/auth, /api/reports, etc.


16. HEALTH CHECK
----------------
The API provides:

    GET /api/health

Expected response:
    {"ok":true}

Local server test:
    curl http://127.0.0.1:5055/api/health

Public HTTPS test:
    curl https://api.example.com/api/health

A successful public health check confirms:
- DNS is resolving.
- HTTPS/TLS is working.
- The reverse proxy can reach Node.js.
- The API process is responding.


17. SERVER STATUS CHECK
-----------------------
The API also exposes:

    GET /api/server/status

On Linux this uses:
- /proc/stat for CPU usage.
- df -P for filesystem statistics.

This endpoint is useful for confirming that the Linux-specific system monitoring
features work correctly.


18. MINIMUM TEST ACCEPTANCE CHECKLIST
------------------------------------
Before pointing the GitHub Pages UI to the server, confirm all of the following:

[ ] Linux server is running.
[ ] Node.js 18+ and npm are installed.
[ ] Maintenix repository is checked out.
[ ] npm ci completes successfully inside Server_API.
[ ] npm run start:all starts without errors.
[ ] API, servicing worker and call-out worker are all running.
[ ] http://127.0.0.1:5055/api/health returns {"ok":true}.
[ ] Server_API/data is writable by the service account.
[ ] Persistent data is backed up.
[ ] HTTPS hostname resolves to the server.
[ ] Valid TLS certificate is installed.
[ ] HTTPS reverse proxy forwards to 127.0.0.1:5055.
[ ] https://<api-host>/api/health returns {"ok":true}.
[ ] Firewall exposes only the necessary ports.
[ ] GitHub Pages origin is allowed by CORS.
[ ] MAINTENIX_API_BASE_URL is set to the HTTPS API origin.
[ ] The deploy branch has been rebuilt after changing MAINTENIX_API_BASE_URL.
[ ] Login and normal API operations work from the GitHub Pages Web UI.


19. CURRENT SERVER-SIDE START COMMAND
-------------------------------------
Production/test stack:

    cd /path/to/Maintenix/Server_API
    npm ci
    npm run start:all

The command starts the current API plus both background workers.


SUMMARY
-------
The most important requirements for the GitHub Pages testing arrangement are:

1. Linux.
2. Node.js 18+ and npm.
3. A writable/persistent Server_API/data directory.
4. API + servicing worker + call-out worker running.
5. API available internally on port 5055 (or configured PORT).
6. A valid HTTPS reverse proxy/domain for browser access.
7. CORS allowing https://mrclubbe-git.github.io.
8. GitHub MAINTENIX_API_BASE_URL pointing to that HTTPS API origin.
9. Backups and process supervision for reliable testing.
